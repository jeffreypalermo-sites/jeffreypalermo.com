## 2. Goals

1. A modern, professional personal-brand site that states your current positioning.
2. **The site itself is the showcase.** Its repo, pipeline, infrastructure and architecture are public and documented as a reference implementation of GitOps, DevOps and Onion Architecture on .NET.
3. **Zero SEO loss.** Every existing URL resolves, the RSS feed survives, and comments are preserved.
4. Room to grow: talks, books, podcast, newsletter, labs and demos on subdomains.

## 3. Options

### Option A: Stay on WordPress, re-theme
Swap P2 Breathe for a modern block theme, rewrite the About and home pages, and fix the tags.
- **Effort:** days. **Cost:** current WP.com Business plan (~$300/yr).
- ✅ Lowest risk. ❌ Showcases nothing about .NET, GitOps or DevOps, so it **fails goal 2**. Not recommended.

### Option B: Headless WordPress + .NET front end
Keep WP.com as the CMS and build an ASP.NET Core front end that reads the WP REST API.
- ✅ Familiar authoring. ❌ You keep paying for WP and its attack surface, content stays outside git (weak GitOps story), and you get two systems to run. Not recommended.

### Option C: Static site generated by .NET
Markdown content in git, built into static HTML by a .NET generator (Statiq.Web, or a small custom Razor-based generator), hosted on Azure Static Web Apps or GitHub Pages behind a CDN.
- **Cost:** ~$0–10/mo. **Effort:** 2–4 weeks.
- ✅ Fastest, cheapest and most secure, with PR preview environments for free on SWA. Content-as-code is a real GitOps story.
- ❌ Thin "architecture on .NET" story: no runtime, no observability, no server-side domain. Statiq's momentum has slowed, so you'd likely own the generator.

### Option D (recommended): ASP.NET Core app + content-as-code + GitOps-delivered infrastructure
A real .NET 10 web application (Razor Pages or Blazor static SSR), structured as **Onion Architecture**, that reads Markdown content from the repo. It's deployed as a container to **Azure Container Apps** (scale-to-zero), with infrastructure-as-code and environment promotion driven entirely from git.
- **Cost:** ~$5–30/mo depending on CDN choice (Cloudflare free tier in front ≈ low end, Azure Front Door Standard ≈ +$35/mo).
- **Effort:** ~4–8 weeks part-time for parity plus the showcase layer.
- ✅ Hits every goal. You eat your own cooking: the patterns from *.NET DevOps for Azure* and Onion Architecture running live, publicly, on your own domain.
- ✅ Output caching and CDN give static-site speed. Also gives you a server runtime for the "do more" features (search, newsletter signup, Ask-the-archive AI, live DORA metrics).
- ❌ More moving parts than C, which is the point, but it must be kept lean.

### Option E: Option D on Kubernetes (AKS + Flux/Argo CD)
"Pure" pull-based GitOps.
- ✅ The canonical GitOps demo. ❌ ~$75–150+/mo minimum and real operational overhead for a personal site. Better as a **later, separate `labs.` subdomain** demo than as the main site's host.

### Option D-S: Option D's architecture, published as an Azure Static Web App
The same Onion-structured .NET 10 app and the same content-as-code repo. The difference is *when* it runs: **at publish time in CI**, not at request time. The pipeline renders every route to static HTML and deploys the output to **Azure Static Web Apps (SWA)**. Dynamic needs go to SWA's managed **.NET 10 isolated Azure Functions** API (`/api/*`). See §4a.
- **Cost:** ~$0.50–10/mo (SWA Free or Standard at ~$9/mo, plus an Azure DNS zone).
- ✅ Static-site speed, security and cost, while keeping D's architecture, tests and GitOps story. PR preview environments are built into SWA. Every deploy is an immutable snapshot.
- ✅ Strong architecture talking point: Onion lets you swap the *delivery mechanism* (request-time vs publish-time) without touching Core.
- ❌ No server-side request pipeline. Legacy redirects, request telemetry and dynamic features need the workarounds in §4a.

## 4a. Option D-S detail: publish-time rendering to Azure Static Web Apps

### How "transform on publish" works
```
git push / PR ──► GitHub Actions
                   1. dotnet build + unit tests
                   2. SiteBuilder: boot UI.Web in-process (WebApplicationFactory/TestServer),
                      enumerate every route from IContentRepository, GET each one, write /dist/**/index.html
                      + feed.xml, sitemap.xml, search index, redirect stubs, staticwebapp.config.json
                   3. Integration tests over /dist: every legacy URL in the oracle resolves; links valid; feed valid
                   4. Playwright against /dist served by the SWA CLI (exactly the bytes that will ship)
                   5. Azure/static-web-apps-deploy (skip_app_build: true) ──► PR preview env  or  production
```
- **The same app is the dev server and the generator.** You run `dotnet watch` locally for live editing, and CI snapshots it to HTML. There's no separate templating engine to learn, and tests exercise the same routing and Razor code both ways.
- **Scheduled publishing and freshness:** a nightly scheduled workflow rebuilds the site. Future-dated posts go live on their date, and DORA metrics and GitHub stats refresh.
- **Infrastructure:** Bicep defines the SWA resource, custom domains and the Azure DNS zone. CI logs in with OIDC and fetches the SWA deployment token at deploy time, so there's no long-lived secret in the repo.

### SWA constraints that shape the design (verified against Microsoft Learn, 2026-10-05)
| Constraint | Impact | Design response |
|---|---|---|
| `staticwebapp.config.json` max **20 KB**. Route wildcards only at the **end** of a path, with no capture/substitution | ~966 `/blog/{slug}/` → `/{yyyy}/{mm}/{slug}/` redirects (~70+ KB) **won't fit** as config rules | Generate a **redirect stub page** per legacy URL (`/blog/{slug}/index.html` with `rel=canonical` plus an instant meta-refresh, which Google treats as a permanent redirect). Upgrade path for true 301s: Cloudflare Bulk Redirects in front, or a `/blog/*` → Functions redirect handler |
| Routes match the **path only**, not the query string or host | `/?p={id}` can't be redirected by config, and `feeds.jeffreypalermo.com` can't be special-cased | `?p=` → tiny inline script on the home page using a generated id→URL map (rare traffic). `feeds.` → a **second free SWA** whose only rule is `/*` → 301 `https://jeffreypalermo.com/feed/` |
| Free plan: 2 custom domains, 3 preview envs, 250 MB per environment, 15,000 files | Apex + `www` uses both domains, so `feeds.` lives on the separate app above. ~966 posts + ~966 stubs + taxonomy pages + 276 media files is well under 15k files. Verify media size during export | Start on **Free**. Move to **Standard (~$9/mo)** for 10 preview envs, an SLA and the 500 MB limit |
| Apex domain on SWA needs ALIAS/flattened records | Plain CNAME at the apex isn't allowed | Azure DNS alias record (or Cloudflare CNAME flattening) |
| No server request pipeline | No server-side request telemetry or output caching (not needed) | App Insights browser SDK for page telemetry. Functions emit OpenTelemetry for API calls |

### Generator choice: custom .NET vs an off-the-shelf SSG (all free / OSS)

At ~1,000 posts, build speed isn't the deciding factor for any of these. The decision is **toolchain and showcase story**.

| Generator | License / lang | Fit for this site | Notes |
|---|---|---|---|
| **Astro 6** | MIT · TypeScript/Node | ⭐ Best modern content-site DX | Content Collections = typed Markdown/MDX with a Zod schema (validated at build). Ships zero JS by default, with "islands" where needed. Official RSS, sitemap and MDX integrations; Pagefind search. `redirects` config emits meta-refresh pages in static mode (same approach as §4a). Large theme ecosystem. **Acquired by Cloudflare (Jan 2026)**, staying MIT and multi-host; deploys fine to Azure SWA |
| **Hugo** | Apache-2.0 · Go single binary | Strong | Fastest builds; `aliases` front matter handles legacy URLs natively; built-in taxonomies and RSS. Go templates are the least pleasant to author |
| **Eleventy (11ty) 3** | MIT · JS/Node | Good | Simplest mental model ("just give me HTML"), flexible templating. Less structure and typing than Astro |
| Zola | MIT · Rust single binary | OK | Hugo-like simplicity, smaller ecosystem |
| Jekyll | MIT · Ruby | Weak | Native to GitHub Pages, but aging and slow |
| Next.js static export | MIT · React | Overkill | React runtime for a mostly-text site; Vercel-centric |
| Statiq Web | MIT/commercial · .NET | Risky | The only mature .NET SSG, but the core is still **1.0 beta, last release Jan 2024** |
| **Custom .NET generator (§4a)** | your code · .NET 10 | Best *.NET* story | Razor rendered at publish time. You own the generator (~a few hundred lines, but it's yours to maintain) |

**The real trade-off: Astro (best site) vs custom .NET (purest .NET story).**
- **Astro + .NET hybrid** puts the presentation layer in Astro and **.NET everywhere behind it**: the `Tools.WpMigrator` (C#), the SWA API (.NET 10 isolated Functions: newsletter, Ask-the-archive, redirects), and the full-system tests in **Playwright for .NET** (C#/xUnit). Infra is in Bicep. Story: "a best-of-breed front end on a .NET core." Fastest path to a site that *looks* great.
- **Custom .NET (D-S)**: every byte comes from .NET and Onion layering runs end to end. Story: "here's how to build a static site in .NET". More to build and maintain, and a smaller theme/component ecosystem.

**Free hosting note:** Azure SWA Free, Cloudflare Pages/Workers and GitHub Pages are all $0 for this site. Cloudflare's `_redirects` file supports **~2,000 static redirects**, which would give true 301s for all ~966 `/blog/{slug}/` URLs. SWA's 20 KB config can't do that.

### Repo shape changes vs D
- `src/UI.Web` stays (dev server and render source). Add **`src/SiteBuilder`** (route enumeration + snapshot) and **`src/Api`** (.NET 10 isolated Functions).
- `infra/` drops Container Apps, ACR and Log Analytics. It's just SWA, DNS and App Insights.
- No container image. The deploy artifact is the `/dist` folder, attached to each workflow run, so any release can be redeployed byte-for-byte.

## 4b. Requirement: preserve ALL old URLs (changes the recommendation)

### What "all" means: URL inventory (Wayback Machine CDX, 4,833 distinct URLs ever captured)
| Class | Example | Works today? | Static host can do it? |
|---|---|---|---|
| Posts | `/2008/07/the-onion-architecture-part-1/` | ✅ 200 | ✅ |
| No trailing slash | `/2008/07/the-onion-architecture-part-1` | ✅ 301 | ✅ (host setting) |
| **Wrong case** | `/2008/07/The-Onion-Architecture-Part-1/` | ✅ 200 | ❌ static file paths are case-sensitive |
| **Graffiti-era `/blog/{slug}/`** (~329) | `/blog/getting-started-with-the-asp.net-mvc-framework-…/` → `/2008/08/…asp-net-mvc…/` | ✅ 301 via WP's **fuzzy slug guesser** (dots→dashes, prefix match) | ❌ / meta-refresh only |

| Comment anchors | `#comment-1234` | ✅ | ✅ (keep the same element ids) |

Partial live check (1,782 of 4,833 URLs before the run was interrupted): 1,441 → 200, 184 → 404, 145 → 403 (WP.com system paths). The full run becomes the committed **URL contract** test.

**Conclusion:** about a third of the legacy surface (the bolded rows) is behavior, not files. Case-insensitivity, fuzzy slug matching, query-string routing and host routing need **code that runs on every request**. No static host does this alone, whatever generator builds the files.

### Does Astro support URL preservation?
- **Static mode (default):** `redirects` config emits **meta-refresh HTML pages**. Per the docs, the status code "is not used by the server". It can't see query strings, case variants or hosts.
- **Static mode + host adapter** (Cloudflare, Netlify, Vercel): adapters write `redirects` into the host's own redirect file for real 301s, but still path-only. There's no official Azure SWA adapter.
- **On-demand (server) mode** with `@astrojs/node`: middleware runs **per request** and can do everything above. Middleware for *prerendered* pages runs **only at build time**, so the legacy-URL logic has to run in front of the static files. At that point you're running a Node server.

So Astro *can* do it, but only by becoming a Node server, and that makes the runtime JavaScript, not .NET.

### Revised recommendation: Option D, ASP.NET Core serves everything
Since a request-time server is mandatory, make it the .NET showcase:
- **ASP.NET Core (.NET 10)** renders pages (Razor/Blazor SSR) **and** owns URL preservation: a `LegacyUrlResolver` in Core (pure, unit-tested) plus middleware in UI.Web. It covers case-insensitive lookup, the `/blog/` fuzzy matcher, `?p=`/`?feed=`/`?m=`, per-post feeds, the `feeds.` host and **restored** Community Server `.aspx` links (mapped from Wayback titles).
- **"Transform on publish" is kept**: CI parses all Markdown into a content index **baked into the immutable container image**. One commit = one image = one content snapshot. There's no runtime database.
- **Static-like performance and cost**: output caching plus a CDN (Cloudflare free or Front Door) in front. Azure Container Apps or App Service B1, ~$10–20/mo.
- The **URL contract** (all 4,833 URLs plus each one's expected status/target) runs as an integration test on every PR.

## 5. Migration plan

### Phase 0: Protect the asset (this week)
1. **Renew the domain**. It expires 2026-12-29. Turn on auto-renew and registrar lock.
2. Take a full **WordPress.com export** (WXR plus a media export) and archive it in cold storage.
3. Crawl and record the current URL inventory (wp-sitemap.xml plus the REST API) as the **redirect test oracle**.
4. Pull Google Search Console data, if you have it, to identify the top-traffic and top-linked URLs.

### Phase 1: Content extraction (week 1)
- `Tools.WpMigrator` (C#) reads the WP REST API or WXR and does the following:
  - Converts HTML to Markdown, keeping raw HTML where conversion is lossy (2004-era markup).
  - Downloads originals from `wp-content/uploads`, strips Photon (`i0.wp.com`) URLs and rewrites them to local media.
  - Rewrites internal links: `http://jeffreypalermo.com/blog/{slug}/` → canonical `https://…/{yyyy}/{mm}/{slug}/`, and `feeds.jeffreypalermo.com/…` → `/feed/`.
  - Exports the 2,708 comments as static archived data, rendered under each post.
  - Normalizes the 27 tags into a small, clean taxonomy (e.g. *Architecture, DevOps, ASP.NET, Agile & Teams, Community*).
- Output is committed to `content/` as one PR, which makes it reviewable and reversible.

### Phase 2: Build the app (weeks 2–5)
- Home page that positions **who you are now**: Chief Architect at Clear Measure, books, podcast, talks, and a CTA (newsletter / contact / Clear Measure).
- Featured **Onion Architecture hub page** that ties parts 1–4 together plus newer material. This is your most-linked asset.
- Archive by year, tag pages, search (client-side index or server-side), RSS/Atom at the same `/feed/` URL.
- An "era" banner on posts older than ~5 years ("Written in 2005, technology details may be dated").
- New comments via **giscus** (GitHub Discussions), which fits the git-centric theme. Old comments stay as a read-only archive.

### Phase 3: Infrastructure and pipeline (weeks 3–6, in parallel)
- Bicep for all Azure resources, OIDC GitHub → Azure, PR environments, production promotion.
- Stand up the **staging host** (e.g. `next.jeffreypalermo.com`) and run the URL-oracle test suite against it until there are zero failures.

### Phase 4: DNS and cutover (week 6–7)
1. **Move DNS off WordPress.com first** (to Azure DNS or Cloudflare), still pointing at WP. Recreate exactly:
   - A/CNAME for apex and `www`
   - **MX → GoDaddy** (`smtp.secureserver.net` 0, `mailstore1.secureserver.net` 10)
   - Fix SPF: `v=spf1 include:secureserver.net ~all` (adjust to whatever actually sends mail), and add **DMARC** (`p=none` to start)
   - `feeds` CNAME → the new site (it currently points at dead FeedBurner)
2. Lower TTLs, cut apex/`www` over to the new site, and run the redirect oracle against production.
3. Watch 404 logs and Search Console for 2–4 weeks. Keep WP.com in read-only/private mode for 30 days as a rollback, then cancel it.

### Redirect matrix (must be covered by integration tests)
| Legacy | Target |
|---|---|
| `/{yyyy}/{mm}/{slug}/` | same (canonical, unchanged) |
| `/blog/{slug}/` | 301 → canonical |
| `/?p={id}` | 301 → canonical (WP post id kept in front matter) |
| `/tag/{x}/`, `/category/{x}/` | 301 → normalized tag page |
| `/feed/`, `/comments/feed/` | same URL, new feed |
| `/wp-content/uploads/{…}` | serve same path (preserve folder structure) |
| `feeds.jeffreypalermo.com/*` | 301 → `/feed/` |

`wp.me/uJDT…` shortlinks are owned by WordPress.com. They'll break when the site leaves WP.com, which is acceptable.
